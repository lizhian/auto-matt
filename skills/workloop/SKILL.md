# Workloop 开发流程

主 agent 负责与用户讨论、派工、集成和交付。使用当前宿主的原生子 agent 能力，任务说明、用户沟通、审查和交付报告使用中文。子 agent 把需要用户决定的问题交回主 agent。纯讨论或只读评估以回答问题为止。

## 选择路线

先读项目约定及相关实现。依据变更影响、尚未确定的行为和验证难度推荐路线，尊重用户已指定的路线。已知的需求和决定直接带入下一步。遇到实质取舍时由主 agent 用具体例子提问，必要时使用 `grilling`；涉及领域术语或架构决定时参考项目术语表和 ADR。

| 路线 | 适用情况 | 执行方式 |
| --- | --- | --- |
| 快速 | 行为明确、改动局部可逆，有直接验证方法 | 主 agent 将目标和验证方法直接交给一个实现子 agent，核对改动和结果后交付。 |
| 单票 | 范围集中，但改动值得独立审查 | 一张票描述完整需求，一个实现子 agent、一名独立审查子 agent，通过后集成。 |
| 多票 | 存在多个可独立验收的切片、跨模块契约或交付依赖 | 先写 Spec，再拆票。按依赖派工，逐票审查、串行集成，最后审查整个集成版本。 |

快速路线的发现若改变了范围或风险，把现有改动、证据和待定问题带入单票或多票路线。涉及权限等高影响行为时，即使改动只有一行，也应考虑独立审查。

## 从需求到派工

- 快速路线在对话里交接即可。单票以票据本身作为实现依据。多票使用项目现有的 Spec 和票据惯例；可用时用 `to-spec`、`to-tickets` 整理已达成的决定。外部发布按用户已有授权执行，票据也可以保存在本地。
- 每票写明目标、范围、须保留的行为、依赖及编号验收条件。每条条件附能证明结果的测试命令或人工观察步骤。开工前由用户确认票据及条件，已经明确确认的版本可直接使用。后续若改变验收口径，交回用户决定。
- 主 agent 记录基线、已有工作区改动和各票状态，向子 agent 提供可访问的票据正文、工作目录、负责范围及验收方法。多票并行写入时给各实现者独立工作区，从包含其依赖的集成版本起步。宿主只提供共享工作区时，串行安排写入。

## 实现、审查与返工

1. **实现。** 创建原生实现子 agent，要求按项目习惯实现和验证。采用 `implement` 时在委派指令中明确，审查由主 agent 按本路线安排，跳过该技能末尾的审查派工。实现者回报实际改动、候选提交或限定范围的补丁，以及各验收条件对应的结果。未执行的验证写明原因。
2. **审查。** 单票和多票各由主 agent 为每票创建独立审查子 agent。交接基线、固定候选版本、票据和证据，要求直接核对实际 diff。阻塞发现须指出违反的验收条件，或有证据的回归、数据丢失、安全问题、既有 ADR 冲突，并给出位置和复现或判断依据。超出本票的改进记为建议。
3. **返工。** 集成前将发现交回原实现子 agent，在同一工作区修复。交给审查者复核原问题及修复引入的风险。反复修复仍未解决同一问题时，报告原因和可选方案。只有用户明确接受的阻塞项可带理由放行。
4. **集成。** 主 agent 逐票集成实际审过的候选，保留用户原有改动。若冲突处理改变了候选行为，复核变动部分。在集成版本执行本票及此前已集成票据的验收，同一命令运行一次即可覆盖多项条件。验证通过后解锁依赖票。集成后发现缺陷，从当前集成版本开修复票。

## 终审、恢复与交付

多票路线由一名新的独立审查子 agent 对照 Spec、各票验收证据和总 diff 检查最终集成版本，重点核对跨票接口及组合后的行为。终审覆盖的版本与交付版本应一致。

任务中断时，从已有票据、候选版本、工作区状态、验证结果和未决事项继续。原子 agent 可以续接时优先续接；需要替换时把这些证据交给接手者。保留未集成的工作供恢复。

交付时报告路线、交付版本或补丁、逐项验收结果、审查发现及处理、用户接受的遗留项。列出实际子 agent 的角色、技能、产出和可核实耗时，缺失时间标为“未记录”。出现反复返工或跨票回归时，简述原因和一条可采取的改进，供用户决定。

## 按阶段使用配套资源

快速路线直接派工。单票或多票启动时读取[运行手册](reference/run.md)，按其中的模板发给实际负责的子 agent。验证已提交的候选时读取[验证手册](reference/validation.md)。会话中断、候选版本发生变化或需要交接时读取[恢复手册](reference/recovery.md)。
