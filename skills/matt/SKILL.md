# Matt 工作流

主 agent 持有用户对话、阶段进度和最终交付。每个阶段按名读取已安装的 Matt 技能。如果技能列表省略了显式调用的技能，到项目和用户技能目录按 `SKILL.md` 的 `name` 查找，兼容 `mattpocock_skills__<name>` 目录。宿主没有 Skill 工具时，直接读取对应文件及它调用的技能。委派时传入技能路径和阶段输入，主 agent 负责调度。若缺少必要技能或委派能力，说明具体卡在哪个阶段。

## 1. 主 agent 主持访谈并确认方案

用户只要求审视或评估时，以只读方式开展访谈和检查，交付发现、依据和建议即完成本次请求。用户随后明确要求落实建议时，沿用已确认的内容，从尚待确认的方案或路线选择继续。

记录整次运行的开始时间。每个委派者在创建子 agent 时记下其标识、委派者和任务，优先从宿主运行事件取得开始、结束时间。子 agent 交付时回报实际使用的技能、工作及结果，一并返回自己委派的子 agent 明细，供主 agent 汇总。

确定目标项目根目录，读取项目指令。查看根目录的 `AGENTS.md`、`CLAUDE.md` 及其中的 `Agent skills` 配置。以配置内可用的 issue tracker 和领域文档规则为初始化证据，通常对应 `docs/agents/issue-tracker.md` 和 `docs/agents/domain.md`。标签配置只有项目启用时才需要。

主 agent 在主对话中亲自执行 grill。已初始化时使用 `grill-with-docs`，按项目约定记录议定的术语和 ADR。未初始化或缺少必要配置时使用 `grill-me`。局部问题由主 agent 直接查阅相关代码和文档，用具体例子确认行为。查证涉及多个可独立调查的问题时，可按需委派。对影响用户可见行为、范围或验收的取舍，由主 agent 给出具体问题和推荐答案，逐轮等待用户回复。

讨论收敛后，主 agent 用用户可核对的行为和验收标准概括方案，询问是否按此方案执行，然后停在这一步。即使是简单需求，也要收到用户对该方案的明确确认才能展示路线。用户提出修正时，更新方案再请其确认。

## 2. 主 agent 展示路线，由用户选择

方案确认后，主 agent 在主对话中列出以下三条路线，结合本次任务的变更边界、契约和依赖推荐一项，并说明理由。询问用户选择哪条路线，等待实际回复。用户指明路线或回复“按推荐走”后，才开始该路线的规划、Spec 编写或实现委派。

| 选项 | 判断依据 | 后续流程 |
| --- | --- | --- |
| 简单 | 影响局部，变更和验证可以由单个实现者清楚处理 | 主 agent 用 Plan Mode 产出短计划 → 实现子 agent 用 `implement` 并完成内置审查 → 一名独立子 agent 直接复核最终 diff |
| 中等 | 需要将行为、接口或验收标准写入可引用的 Spec，整体仍适合一个实现者 | 主 agent 用 `to-spec` 产出 Spec → 实现子 agent 用 `implement` → 独立审查子 agent 用 `code-review` |
| 复杂 | 有多个可独立验证的交付切片，依赖排序或并行能减少协调成本 | 主 agent 用 `to-spec` 和 `to-tickets` → 用 `implement-spec` 调度并行实现子 agent → 独立审查子 agent 用 `code-review` |

## 3. 产出实现依据并委派

向独立 worktree 中的子 agent 交接本地 Spec 和票据时，提供该子 agent 可读取的绝对路径。若双方无法共享文件，随任务附上相关 Spec 内容、本票正文、依赖和验收标准。

- **简单**。主 agent 在宿主的 Plan Mode 下生成短计划，沿用用户已确认的例子作为验收标准，补充改动位置和验证方法，交给实现者和审查者。若模式由用户控制，提示在该阶段切换，产出计划后回到允许实施的模式。若宿主没有 Plan Mode，在主对话先完成只读规划，并注明实际采用的方式。
- **中等和复杂**。主 agent 把确认过的访谈结论交给 `to-spec`。复杂路线再用 `to-tickets` 生成带阻塞关系和验收标准的纵向切片，提交用户确认切分和依赖。测试入口与设计沿用访谈中已确认的决定，只有出现新取舍才重新讨论。优先使用项目约定的 tracker 和文档位置。未配置 tracker 或本次未授权发布到外部时，使用项目惯例目录或 `.scratch/<feature>/spec.md` 及同目录下的 `issues/`。将本地文件作为本次 tracker 交接给出，供 `to-spec`、`to-tickets`、`implement-spec` 和审查读取，标签沿用技能的默认值。
- **实现**。开始前记录实现基线，Git 项目通常使用本次实现前的提交 SHA，并识别工作区原有改动。简单或中等路线交给一个 `implement` 子 agent。复杂路线由主 agent 按 `implement-spec` 调度，以独立 worktree 实现互不阻塞的票据，受宿主并发上限约束。主 agent 串行集成。每合入一票，在新的集成版本上执行本票及此前已集成票据约定的验收检查。多项标准共用的检查只执行一次，结果关联到各项标准。若出现回归，先定位并修复，通过后再启动依赖该版本的票据。交接包含计划或 Spec、票据、验收标准、已约定的验证及基线。

`implement` 和 `implement-spec` 各自按其技能指令调用 `code-review`，再进入主 agent 的独立审查阶段。`implement-spec` 收尾时的 PR 转待审和关闭票据由主 agent 在独立审查后处理。

在现有计划、Spec 或票据内，为每项已确认的验收行为写明验证方法。优先引用能直接证明该行为的现有测试或命令；适合人工观察的，写明操作和预期。实现者逐项回报实际结果和证据，未执行的项注明原因。两轮审查都接收这些证据、各自的基线和对应的计划或 Spec。复杂路线终审使用最终集成版本的累计验收结果。提交后的审查使用固定的目标 SHA。提交前将本次实现的补丁作为审查者的 diff 输入，收齐暂存、未暂存及新增文件中的相关改动。用隔离工作区或限定范围的补丁排除工作区原有改动。

## 4. 独立审查并交付

实现与集成完成后，主 agent 将最终 diff 和验收依据交给一名未参与实现或首轮审查的新子 agent。

- **简单路线**。附上首轮审查结论及此后的改动。由该子 agent 独自阅读最终 diff，直接复核下列三项。首轮后有实质修改时，再核对受影响的验收行为。此轮不调用 `code-review`，也不拆分审查任务。
- **中等和复杂路线**。独立审查子 agent 调用 `code-review`。宿主允许嵌套委派时按该技能运行双轴子 agent。宿主限制嵌套时，由审查子 agent 检查两轴。

独立审查围绕以下三项给出代码或项目依据。

- 改动是否合理，是否适合现有代码结构并保留预期行为。
- 改动是否是实现已确认功能所需的最小范围，具体指出可省掉的改动或可复用的现有实现。
- 改动是否符合项目明文规范及同类代码的现有习惯。

主 agent 处理可证实且在范围内的问题，重跑受影响的验证。若修复实质性改变了已审查的代码，对变动部分重新审查。核实最终结果符合验收标准后，再执行本次已授权的 PR 转待审或关闭票据。其他外部发布、推送或创建 PR 使用本次已有的授权。

## 5. 汇总本次执行

- **结果概览**。写明所选路线、交付物、每项验收行为对应的证据和结果、两轮审查各自的发现与处理情况，以及未完成事项。报告子 agent 去重总数和从开始到交付的墙钟耗时，包含等待用户的时间。并行任务分别计时。
- **逐 agent 明细表**。每个实际创建的子 agent 一行，含嵌套委派。列为「子 agent｜委派者｜实际使用的技能｜具体工作｜结果或产出｜开始｜结束｜耗时」。同一 agent 续接多轮时在同一行列出各段时长。没有使用技能填“无”，缺少依据的字段填“未记录”。若只有委派和收到结果的时间，明确标为“委派至回报”，与实际运行时间区分。
- **流程图**。每次按实际经过的阶段和委派关系绘制，标出主 agent、具体执行者及两轮审查发生的位置，名称与表格一致。
- **甘特图**。有可靠起止记录时，在同一时间轴展示已知执行区间，保留并行重叠。时间不全的 agent 仍列入表中，并说明图覆盖了哪些记录；所有区间均缺失时只交付表格和流程图。
