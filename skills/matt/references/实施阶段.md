# 实施阶段

用户已明确选择路线时，直接进入该路线的规划。否则展示以下三条路线，结合范围、验收条件和依赖关系推荐一条，说明理由并等待用户选择。

拟定计划或 Spec 时，对照[收敛标准](收敛标准.md)，写明本次改动范围、相关项目惯例和必要的验收行为，一并请用户确认。用户提出修改时，更新后再确认。

| 路线 | 适用情况 | 执行顺序 |
| --- | --- | --- |
| 简单 | 改动局部，短计划即可说明如何实现和验证 | 主 agent 使用计划模式生成计划。宿主无此模式时，在主对话中写出短计划。用户确认计划后，由主 agent 直接实现或委派子 agent 实现。 |
| 普通 | 需要明确行为、接口或验收标准，适合一个实现者 | 主 agent 使用 `to-spec` 生成 Spec。用户确认 Spec 后，主 agent 委派一个子 agent 使用 `implement` 实现。 |
| 复杂 | 有多个可独立验收的切片，需要协调依赖或并行工作 | 主 agent 使用 `to-spec` 生成 Spec。用户确认 Spec 后，进入 `to-tickets`，结合本次功能给出拆分粒度选项，说明每种粒度下一个切片大致交付什么。等待用户选择后按该粒度拆分，按技能要求核对切片与依赖，再使用 `implement-spec` 实现。 |

使用 `to-spec` 时先生成草稿，用户确认全文后，再按项目配置和本次授权发布。只有访谈技能的选择依赖根目录的 `GLOSSARY.md`。需要发布 Spec 或票据时，单独核实项目配置的跟踪器及发布位置。

## 实现与复核

按已确认的计划、Spec 或票据开工。委派时提供可读取的材料、验收条件、内置审查的 diff 范围和交回时机。复杂路线逐票集成，在集成版本上验证本票及受影响的既有行为，通过后再启动依赖该版本的票据。改动共享接口或依赖关系时，覆盖受影响的调用方；项目已有快速全量检查时可直接使用。全部票据集成后，对照完整 Spec 验收一次。调用 `implement-spec` 时约定在集成和内置审查完成后交回主 agent，将 PR 转待审或关票留到最终复核通过后。

实现者交回改动范围、逐项验收结果、未验证项，以及 `implement` 或 `implement-spec` 自带的 `code-review` 结论。主 agent 将验收依据和最终 diff 交给一名未参与实现或首轮审查的新子 agent。

- **简单路线**由该子 agent 独自按[收敛标准](收敛标准.md)阅读最终 diff，直接复核。
- **普通和复杂路线**保留实现技能的内置审查。独立审查者使用 `code-review` 复核最终 diff，重点检查收敛标准。宿主限制嵌套委派时，由审查者直接检查规范和需求两轴。已有结论能回答本次检查项，且相关代码和依赖行为均未变化时，可引用其依据，集中核查遗漏和后续修改。

主 agent 处理范围内有依据的问题，补齐验收缺口，重跑受影响的验证。实质修改过的部分交回独立审查者复核。最终验收与复核通过后，由主 agent 执行已授权的 PR 转待审或关票，然后进入[总结阶段](总结阶段.md)。
